# 界面设计决策

这份文档记录 MiniDocs 界面上的**取舍**——为什么这样做，以及哪种做法试过但不行。

代码里只留功能性注释（"这样写会静默出错"那一类），设计理由统一放在这里。理由是 CSS
里的长篇解释会随样式一起被读到、却与代码逻辑混在一起；而设计决策的读者通常是**要改
这个决定的人**，他需要的是上下文而不是就近的注释。

新增/修改样式时，如果改动背后有"试过另一种、不行"的故事，请写到这里。

---

## 1. 视觉层级：次要动作必须轻于身份标识

**规则**：同一个区域内，身份的视觉重量 > 主操作 > 次要动作 > 状态提示。

### 失败做法：相邻的色块做视觉配对

工作区顶栏上有两块色块——「知识库标识」与「返回键」。最初让两者共用同一对品牌渐变
（`--md-brand-gradient`），看上去是"一套导航件"。

**实际效果是灾难**：两块**同尺寸、同渐变、同投影**的方块并排，眼睛会当成"一对一样
的按钮"，分不出哪个是库、哪个是返回。投影还让一个次要动作浮了起来，抢了身份标识的
视觉重心。

### 现在的做法

- **知识库标识**：顶栏里唯一的品牌色块（渐变 + 投影）
- **返回键**：无底色，识别度交给**图标颜色**（`--md-primary`），悬停浮出淡底确认热区

> 次要动作在视觉上必须轻于身份标识，这是**排序问题**不是好看问题。

**代码位置**：`admin.css` 的 `.md-ws__logo` / `.md-ws__back`；
`variables.css` 的 `--md-brand-gradient`。

## 2. 工具条的色相体系

工作区顶栏有 8 个按钮。全部染色会变成调色盘，全部中性又认不出谁是谁。

### 三类角色

| 角色 | 按钮 | 处理 |
| --- | --- | --- |
| **主操作** | 保存、提交推送 | 实心主色渐变 |
| **状态** | N 处改动、已同步 | 状态色胶囊（琥珀= 有未提交内容） |
| **功能入口** | 设置 / 分享 / 拉取 / 预览 / 导出 | 色相的极淡底 + 实色图标 |

**一个工具条只能有一个实心块**，否则"最要紧的动作是哪个"没有答案。保存只在编辑态、
提交推送只在云端库，两者不同时出现，不争焦点。

### 功能入口的具体比例

- 常态：底色 = 色相 **8%**、描边 = 色相 **22%**、文字 = 色相压深一档
- 悬停：底色 **15%**、描边 **45%**

八个百分点是"能认出是谁"与"不抢焦点"之间的平衡点。悬停两档之间要有明确的"在响应"
感，但**不用位移或缩放**去强调——那两种在工具条里都太吵。

### 状态色必须与动作色分开

琥珀在别处是警示，在工具条里是"有未提交内容"。混用会让人以为出了故障。

### 停用态要把底色一起褪掉

一排灰按钮里夹一个饱和色块，看起来像还能点。

**代码位置**：`admin.css` 的 `.md-ws__btn--*`；与侧栏 `.md-navitem--*` 共用同一色板。

## 3. 侧栏色相：只给图标上色

十个入口各配一个色相，**文字保持中性**。

- 十行文字铺五种颜色会花成一团，而图标是扫视时最先落眼的地方
- 色相放图标上，辨识度有了，整栏的秩序感还在
- 十个色相挑成**同一档明度与饱和度**（约 600 色阶），而不是各选一个"好看的颜色"——
  明暗不齐的色板放一列会显得是随手调的

激活态**不用色相区分**：底色与字重已经承担了"你在哪"这件事。

**代码位置**：`admin.css` 的 `.md-navitem--*`；暗色另给一套浅色档。

## 4. 图标系统的四种形态

`shared/iconDef.ts` + 两个渲染组件（`user/components/Icon.vue`、
`admin/components/MdIcon.vue`）支持四种形态，各自的坑不一样：

| 形态 | 怎么表达 | 注意 |
| --- | --- | --- |
| 描边线条 | 24×24 `PATHS` 数组 | 默认形态，继承 `currentColor` |
| 单色填充 | `SOLID_ICONS`，viewBox 自带 | 不给 `fills`，继承 `currentColor` →自动适配暗色 |
| **双色** | `SOLID_ICONS` + `fills[]` 逐 path 上色 | 品牌标识天生浅底板 + 深色字形，单色会把底板涂掉 |
| **宽扁** | viewBox 宽高比 > 1.4 | 必须**按高度给尺寸**，让宽度按比例算；塞进固定宽高会被压扁 |

### 为什么给 `fills` 而不是直接写死在 path 上

写死 `#040000` 的图形在暗色模式下会是一块不受控的深色。继承 `currentColor` 才能
跟着按钮文字色走、跟着主题走。

### 覆盖与重名

`SOLID_ICONS` 优先于各组件的 `PATHS`，**同名即覆盖**。所以把线条版改成填充版时，
要记得把线条版从 `PATHS` 里删掉——否则它成了永远不会渲染的死代码。

## 5. 图标选择器：借图标库，不要它的运行时

分享页导航菜单的图标选择器有 240 个图标（Tabler，MIT）。

### 为什么不用 Iconify 的运行时

图标是作者在后台**运行时**挑的，阅读页要按存下来的名字渲染——于是图标数据必须随
应用一起走。而 Iconify 的运行时方案（web 组件 / API 拉取）在这个项目里三条都过不去：

1. **CSP**：`script-src` 只认 `'self'`，CDN 上的 web 组件执行不了
2. **可私有部署**：断网环境拉不到图标 = 分享页图标全挂
3. **产物体积**：门户阅读页刻意保持精简，不该为分享页背一整份图标库

所以只借它的**图标库**：`scripts/gen-nav-glyphs.mjs` 按语义关键词搜 Iconify 的搜索
API、批量取回路径数据、**构建期烤成一个 TS 文件**。零运行时依赖、零 CSP 改动、离线可用。

### 体积控制

初版按宽口径搜出 909 个、310KB，太大。收紧到"每次搜索 10 条 + 总量 240 + 去掉
`-2`/`-filled` 变体"后是 79KB（gzip 约 20KB）。

**验证过门户主 chunk 不含这些数据**——代码分割把它隔离在分享页与管理页。

### 两种找法都得有

- **分节浏览**（文档/分类/时间/…）用于"不知道那图标叫什么"
- **搜索**用于"知道大概意思"，中英文都能搜，命中数截到 300

一次渲染 900 个 svg 会让弹窗卡一下，而导航图标没有"排在第 400 位才想到"的用法。

**代码位置**：`shared/navGlyphs.generated.ts`（生成物，勿手改）、`shared/navIcons.ts`、
`shared/NavGlyph.vue`。

## 6. 滚动条

**视觉宽度约 3px**：`7px` 滑块减去两侧各 `2px` 透明边框
（`background-clip: content-box`）。

**用全局 `*` 规则兜底**是最重要的一步。此前只有 20 处按元素单独写样式，漏掉的那些
退回浏览器默认样式——Windows 上是约 15px 宽、带上下箭头的灰条，落在 300px 的侧栏里
非常扎眼。逐个补规则更容易再犯，用 `*` 覆盖"漏写"这一类。

**元素级规则特异性高于 `*`**，所以那 20 处要改成引用同一组令牌，否则会盖掉全局规则。

**状态色**：常态主色 12%、悬停 30%；暗色 22% / 45%（暗色主色更亮，同样的百分比在深底
上几乎看不见）。

刻意隐藏的三处（工作区操作条、门户分段控件、分享页导航条）保持 `scrollbar-width: none`
——它们靠隐藏滚动条换横向空间，不在"所有滚动条"的诉求范围内。

**代码位置**：`variables.css` 的 `--md-scrollbar-*` 与全局规则。

## 7. 阅读页三栏：贴死，不做浮起的玻璃卡片

侧栏与大纲的**半透明玻璃底色**留着，但几何上**贴死**：不留外边距、不圆角、不投影，
三栏之间各出一条朝内的 1px 发丝线。

**失败做法**：「浮起的圆角卡片」（`margin: 12px` + 圆角 14px + 投影）。在 300px 的栏宽下
四周都是缝，正文夹在两个浮块中间，看上去像三张卡片拼在一起，而不是一个连续的阅读界面。

**侧栏与大纲是导航容器，不是可点击的卡片**，贴死才符合它们的角色。

### 为什么删掉了 `backdrop-filter`

磨玻璃要有东西可磨。面板贴死之后背后是一片纯色底（最多叠着页面光晕），blur 出来的
结果与不 blur 几乎一样——留着等于让一个覆盖整屏高度的模糊层在每次滚动时参与重绘，
换来肉眼看不出的差别。

`--md-glass-blur` 令牌保留：**分享页顶栏**仍在用，那里的背后是正文，blur 有实际作用。

### 分享页正文三栏刻意保持全出血

那是宽屏布局的有意选择。飘着的圆角卡片会破坏它的无缝语言，所以分享页吃新色板与顶栏
玻璃，但三栏不加面板。

**代码位置**：`reader.css` 的 `.md-reading[data-mode='portal']` 系列。

## 8. 分享页导航菜单固定思源黑体

不跟读者的正文字体偏好走：**导航条是站点外壳**（品牌、入口、动作），不是文章内容。
让读者选的正文宋体传染到顶栏几乎没有收益——菜单项就那么几个入口名——反而让顶栏在
不同读者眼里长得不一样。

### 只写 `font-family` 是不够的

绝大多数机器没本地装思源黑体。不注入 webfont 样式表时，浏览器会**安静地落到系统字体**
——界面上看不出任何异常，就是"没生效"，这类问题极难排查。

所以 `readerFont.ts` 导出了 `ensureReaderFontWebfonts(id)`：只挂样式表，不改读者偏好、
不写 `localStorage`。刻意不与 `applyReaderFont` 合并——合起来的话，加载导航字体会顺手
把读者选的正文字体也改掉。

挂在 `ShareMenu` 的 `onMounted`：那里本来就有 `document.fonts.ready` 后重排滑块的逻辑
（中文字体晚到会让按钮宽度变化），字体与滑块在同一步里就绪。

**代码位置**：`variables.css` 的 `--md-share-nav-font`、`reader.css` 的 `.md-share__menu`。

## 9. 门户可见范围：落在 shares，不落在 knowledge_base

门户列表原先只有一道受众闸：发布即对所有人可见。库自己的 `visibility` 管的是平台内
权限（谁能读能管），与对外曝光正交——合成一列会让作者改一个却连带改了另一个。

所以给**分享**加一列 `shares.portal_scope`，三档：

| 档 | 含义 |
| --- | --- |
| `anonymous` | 所有人（含未登录访客）—— 迁移默认值，与历史数据等价 |
| `member` | 任何登录用户 |
| `maintainer` | 仅本库维护者 |

### 阅读侧也要拦（用户确认的口径）

匿名访客直接拿到分享链接也读不到。校验放在**口令判定之前**：受众是更外层的闸，反过来
会让一个不该知道这个库存在的访客先看到"需要口令"，那本身就泄露了库里有东西。

返回 `login` 状态而不是 403——读者需要知道下一步做什么。

### 已知偏差

`maintainer` 档的三个粗筛是 `AccessService` 的**超集**而非复制（真正的裁决仍在权限服务，
避免违反规范 §2.6）。代价：组织管理员对 `owner_only` / `members` 档的库在门户上可能
看不到（他们在控制台里照常能管）。取舍是"门户少露一条"优于"复制一份权限裁决"。

**代码位置**：`share/support/SharePublicationSupport.java`、`Share.java`、
迁移脚本 `V8__share_portal_scope.sql`。

## 10. Git 拉取：默认保留本地改动

原先只有"先提交"或"强制覆盖"两条路，中间那条最常用的情况被堵住了：作者正在写东西，
远程有新提交，他想先把远程的拉下来接着写，却必须先把手头这半篇提交掉。

现在默认走 `git pull --autostash` 的做法：

1. 工作区脏 → 把改动临时收起（**含未跟踪文件**）
2. fetch + merge
3. 把改动放回来

JGit 的 `PullCommand` 内部是 fetch + merge，而 merge 在工作区脏、且远程改动了同一批
文件时会**直接失败**——这就是为什么必须先收起而不是"直接 pull"。

### 两条分支都保证处理 stash

**不做"stash 之后就不管"**：

- 拉取失败 → **放回**。界面上写着"拉取失败"，用户理所当然以为自己的东西还在
- 放回时冲突 → **保留 stash 并把 ref 报进错误消息**。丢掉就等于把"冲突"变成"丢失"

用 `StashApply` + `StashDrop` 而不是 `stashPop`：pop 在冲突时会把 stash 摘掉一半、
ref 就不在了——而那正是要报给用户去恢复它的那串东西。

**代码位置**：`git/GitVaultService.java` 的 `pull` / `doPull` / `restoreStash`。

## 11. 正文字体：换字体时要补字号，不是调行高

读者反馈「设成楷体（霞鹜文楷）后行距怎么这么大，整体看着不佳」。查下来**行高根本不是原因**：

实测（Chrome 155，`font-size` 100px，取「国高面们页的」六个全角字墨迹平均）：

| 字体 | `line-height: normal` | 正文 `1.8` 下的行盒 | 墨迹高占 em | 墨迹宽占 em |
| --- | --- | --- | --- | --- |
| 系统默认（基准） | 1.355em | 27.89px | **94.2%** | 93.5% |
| 微软雅黑 | 1.290em | 27.89px | 94.2% | 93.5% |
| 霞鹜文楷 | 1.419em | **27.89px** | **87.0%** | **81.7%** |
| 系统楷体 KaiTi | 1.097em | 27.89px | 82.8% | 75.8% |

**行盒高度四款完全一样。** 差异全在字面：楷体的字天生比黑体小一圈，
同一个行盒里装了个小字，看着自然就"空"——读者的感受是"行距大"，实际是"字小"。

### 为什么不是调 `line-height`

只把行压紧，字还是小的；而且行高一改，行盒就变了，引用块、表格、代码块的块高跟着变，
读者看到的是"版面被撑开了"而不是"字变了"。早先试过按字体把行高放宽到 2.0，还把引用块里
`p` 的紧凑边距连带盖掉了（那次的实现是另加一条更高特异度的规则，属于自找的）。

### 现在的做法

字号乘一个系数、行高除以同一个系数：

```css
.md-reading[data-mode='share'] .md-markdown {
  font-size: calc(15.5px * var(--md-read-scale));
  line-height: calc(1.8 / var(--md-read-scale));
}
```

**两者相乘不变，行盒高度一点没动**（实测仍是 27.89px），只是把字面放大到与基准字体相当。
霞鹜文楷取 `1.08`（= 94.2% ÷ 87.0%，按墨迹高补；按墨迹宽要 1.14，但行距感是纵向的，
横向的疏朗是这款字体的字形特征，放大过头反而挤）。

效果（实测）：墨迹高 13.48px → 14.56px，系统默认 14.60px；
密度比（行距 ÷ 墨迹高）2.069 → **1.916**，系统默认 **1.912** —— 和读者原本满意的字体对齐了。

### 两个实现细节

- 规则里**先写一份不含 `calc` 的保底值**（`font-size: 15.5px; line-height: 1.8;`）。
  `calc()` 里拿 `var()` 当除数属于较新写法，万一某浏览器不接受，那条声明会整条失效 ——
  对 `line-height` 而言就是回退到继承值，行距会莫名其妙地变掉。有保底在，最坏情况只是"字没被放大"。
- 系数只作用于分享页（`.md-reading[data-mode='share']`），与 `--md-read-font` 同一作用域：
  门户阅读页没有改字体的入口，就不该被这个偏好影响。

**代码位置**：`readerFont.ts` 的 `ReaderFont.scale` / `applyReaderFont`、
`variables.css` 的 `--md-read-scale`、`markdown.css` 的分享页规则。

**怎么量出来的**：`.verify/_genfonttest.mjs` 把 webfont 分片以 data: URL 内联成一个静态页，
用 canvas 逐像素量字形墨迹、用 `getBoundingClientRect` 量行盒，再让无头 Chrome 把结果吐出来。
换字体、加字体时照这个跑一遍就能拿到补偿系数，不必靠肉眼估。

## 12. 正文配色：按元素分工，不按「能上色就上色」

需求是「正文渲染得美观一点，比如有些内容用不同的颜色」。这类需求最容易做成两件事：
把能上色的都上色（长文里变成彩色噪点），或者堆装饰元素（换个文档就露馅）。
这里改成**按元素的使用频次与语义分配颜色**，先普查再动笔。

### 先数，再设计

对线上 406 篇真实文档做了一次元素普查：

| 元素 | 出现的文档数 | 占比 |
| --- | --- | --- |
| 围栏代码 | 344 | 85% |
| 加粗 | 342 | 84% |
| 行内代码 | 316 | 78% |
| 表格 | 299 | 74% |
| 引用 | 284 | 70% |
| 图片 | 126 | 31% |
| 链接 | 52 | 13% |
| Mermaid | 24 | 6% |
| 任务列表 | 12 | 3% |
| 公式 | 4 | 1% |
| 提示块 | **1** | **0.2%** |

结论直接改了设计重点：功夫压在前五项，提示块只做「把硬编码色换成令牌」这种维护性收拾。
顺带还量了密度——加粗平均**每 6 行**出现一处（198536 非空行 / 58907 个 `**` 标记）：
这个密度决定了加粗**不能**上彩色，只能给极轻的色调偏移。

### 色相分工

| 元素 | 色 | 为什么是它 |
| --- | --- | --- |
| h2 / h3 | 蓝→青**渐变条** | 结构色。只用形状不用文字色——标题的黑是阅读的锚点，染了色反而失去层级 |
| h4 | 蓝（文字色） | 层级已深，改用颜色区分，不再加装饰形状 |
| 行内代码 | 青 | 代码是「另一套字符集」，必须和可点击的蓝链一眼分开 |
| 有序列表序号 | 蓝 | 与链接同族但无下划线，不会被误认成可点 |
| 无序列表项目符号 | 青（二级起转灰） | 一级点色提亮，深层收敛，避免整页青点 |
| 表格表头 / 斑马纹 | 蓝（3–11% 透明） | 74% 的文档有表格，靠底纹深浅分行比加线更耐看 |
| 引用块 | 蓝→青渐变条 | 与 h2 同一套竖条语言，读者立刻识别出「这段是引来的」 |
| 加粗 | 蓝 30% 调墨 | 密度太高，只能给「比正文更冷更沉」的一档墨色 |
| `==高亮==` | 琥珀 | 唯一的作者主动画重点入口，给最暖的色做冷暖对比 |
| 代码块 | 顶端蓝→青亮线 | 最高频的块级元素，配最重的一笔装饰 |

### 为什么不复用 `--md-primary` 那几个

`--md-primary` / `--md-accent` / `--md-success` 是照**小面积、短时间**看的场景调的
（按钮、徽标、状态点）。当**大面积、长时间**阅读的正文颜色就不合格：
`#14b8a6` 当文字压在白底上对比度只有 **2.6:1**，远低于正文需要的 4.5:1。
所以另立一组 `--md-ink-*`，统一取「能在白底上当正文文字安全阅读」的那一档，暗色档整组换高明度低饱和。

用法固定成对：`--md-ink-*` 给文字与描边，底色一律 `color-mix(ink N%, transparent)` 现算，
不另立 soft 变量——同一个色相只维护一个值，改色相时底色自动跟着走。

### 两个容易踩的坑

1. **`mark` 的底色不能只靠色相令牌。** 同一个 24% 的浅琥珀，掺在白底上是淡黄，
   掺在 `#0f1117` 上就发橄榄绿——色相没变，但透明度在深底上丢失的饱和度远多于浅底。
   所以 `--md-mark-bg` 在两个主题里各给一档（24% / 34%），而不是让一条 `color-mix` 通吃。
2. **斑马纹与悬停的特异度完全相同**（都算到 0,3,4），靠源码顺序分胜负——
   悬停必须写在斑马纹**之后**，写在前面的话悬停高亮会被斑马纹吃掉。

### `==文字==` 为什么放在前端做

flexmark 的扩展里没有 mark 这一项（只有 Tables / Strikethrough / TaskList / Autolink / Definition）。
而正文里总得有地方能「由作者决定哪句上色」——标题、代码、表格的色都是**结构**给的，不是重点。
所以这一条在 `enhanceMarkdown` 里做——三个宿主（阅读页 / 分享页 / 后台预览）走的是**同一条**
流水线，挂一次三处都有。预览里看不到的语法，作者就无从校对；预览的全部意义就是
「看到读者会看到的东西」。

护栏比功能本身重要——技术文档里 `==` 本身就是比较运算符，误判会静默啃坏正文。
三道限制：内容不能以空白开头或结尾（`a == b == c` 天然不匹配）、内容里不能出现 `=`、
不在 `code / pre / a / mark / kbd` 里动手。

### 原生 HTML 为什么阅读端也渲染

工作区预览本来就会渲染作者写的原生 HTML（居中段落、`<div align>` 之类）。阅读端若把它当纯文本
丢掉，同一篇文档就会「预览居中、阅读变纯文本」——这是用户实际撞到的问题。所以 flexmark
打开 HTML 解析，安全边界整体后移到 `MarkdownSanitizer`（标签 / 属性白名单）与
`enforceSafeUrls`（协议白名单）：脚本、事件处理器、`javascript:` 一律进不来，但
`align="center"` / `style="text-align:center"` 这种纯版式写法不该跟着陪葬。

对齐在过滤前归一成 `md-align-*` 类名（`<center>` 一并转换），所以白名单不必放行 `style`
属性——授权的是「居中」这个意图，而不是任意 CSS；`style` 里除对齐之外的声明（颜色、背景图、
`url()`）全部丢弃。新增标签或属性前先想清楚注入面，并补
`MarkdownHtmlRenderTest` 的 XSS 用例。

### 怎么验的

- `.verify/md/_marktest.ts` — **19 项**护栏测试，直接 import 线上那份 `enhanceMarkdown`，
  含「连跑两遍结果不变」（后处理本来就会被反复调用）。测的是真代码，不复制一份算法过来测。
- `.verify/md/_csscheck.mjs` — 问浏览器**计算值**而不是看截图：`color-mix` 写错时整条声明会被
  静默丢弃，页面照样能看，只是颜色悄悄回退。亮色 / 暗色各查 24 项。
  （第一版这里没判「元素取不到」，于是两条检查因为样例里根本没有那个元素而报了 ok ——
  测试自己骗自己，比不测更糟。）
- `.verify/md/compare.html` — 同一份样例正文、只换样式表的并排对照，可切亮暗。
- 预览台跑的是**真增强脚本**（esbuild 打包的 `enhanceMarkdown`），
  所以代码块外壳、Admonition 的 DOM、`==高亮==` 的转换都是线上真实产出的形状，不是手搓的 div。

### 顺带修掉的文档错误

`docs/USAGE.md` 与 `README.md` 都写着提示块语法是 `!!! TIP "小标题"`，
但前后端源码里**没有任何地方解析三个感叹号**（`enhanceMarkdown` 认的是 GitHub 风格的 `> [!TIP]`），
线上 406 篇文档里 `!!!` 出现 **0** 次。已用测试坐实（`_marktest.ts` 里两条对照用例）
并更正文档；同时补上了原本没写进文档的 `[!IMPORTANT]`，删掉了并不存在的 `DANGER`。

## 13. 代码高亮：令牌覆盖要按普查来，不是照抄某个主题

### 起因

有人问「代码高亮是不是按语法高亮的，比如 Java」。答案是**是** —— 用真 highlight.js 跑一遍就能证明
（`void`→`hljs-type`、`change`→`hljs-title function_`、`new`→`hljs-keyword`、`User`→`hljs-title class_`）。
但顺着查下去发现了三处真问题：

1. **`hljs-params` 没有任何配色**。hljs 把整个 `(User u)` 当一个 token，没有规则它就继承正文色，
   和 `{`、`;` 完全一样 —— 读者看到的签名像「高亮断了一截」。这个类覆盖 **12 种语言**，
   含库里的第一名 Python 和第三名 Java。
2. **`--md-tk-type` 定义了却没人用**（`#953800`，和 `attr` 同值）。于是类名 `User` 和函数名 `change`
   走同一个 `--md-tk-title`，都是紫色 —— Java/TS 里这是两种东西，同色等于没区分。
   而 `new User()` 里的 `User` 有色、`(User u)` 里的 `User` 没色，**同一个类名两种表现**。
3. **库里 106 块代码的围栏名 hljs 不认**，静默不亮（连 console 都不报）：`http` 20 块、
   `powershell` 18、`toml`+`ini` 28、`plain` 8、`env`+`dotenv` 12、`redis` 23、`conf` 9 等。

### 覆盖范围是量出来的

写选择器前先跑三个普查脚本，不靠记忆：

| 脚本 | 干什么 |
| --- | --- |
| `.verify/md/_extract.py` | 在服务器上从 406 篇里抽每种围栏语言的真实代码，导出 `samples.json` |
| `.verify/md/_real.mjs` | 把真实代码喂给真 hljs，收集它**实际吐出来**的 class |
| `.verify/md/_scopes.mjs` | 扫已注册语言模块的 `className` 字面量，补齐全集 |
| `.verify/md/_tokcheck.mjs` | 断言「吐出来的每个 class 都有落点」，漏一条就退出码非 0 |

为什么要扫源码而不是凭记忆：hljs 的 scope 带点，`title.function` 渲染成
`class="hljs-title function_"`。CSS 里写 `.hljs-title.function` **永远匹配不到、且不报错**。
同理 `char.escape` → `hljs-char escape_`。这类错写不会崩，只会静默不生效。

### 色板分工（9 个令牌）

| 令牌 | 管什么 | 为什么单列 |
| --- | --- | --- |
| `keyword` | 关键字、`true/false/null` | — |
| `type` | 类型与**类名** | 必须和函数名分开，见上面第 2 条 |
| `title` | 函数名、章节名、标签名 | — |
| `attr` | JSON 键、**参数表**、对象属性、`${}` 插值 | 都是「附着在主体上的次级名字」，一类 |
| `string` / `number` | 字面量 | — |
| `built_in` | 内建函数/类型 | — |
| `meta` | 注释指令、`<!DOCTYPE>`、标签尖括号 | — |
| `comment` | 注释 | 斜体 |

**有意不给配色的**：`punctuation`（JSON/Rust 的括号逗号）、`operator`（SQL 的 `=` `<>`）——
它们是结构骨架，上色只会让代码块变花。这条写进了 `markdown.css` 的注释里，
免得下次被人当成漏网又补一遍。

`type` 取青（`#0f766e` / `#5eead4`），因为它是这套色板里唯一还没被占用的色相，
且与正文行内代码的青色同源，整页是连着的。

### 顺带修的两件事

- **去掉代码块外壳顶端的蓝→青亮线**。它压在头部工具条上沿，和工具条自己的分隔线叠成双线，
  反而显脏。代码块靠底色和边框已经足够从正文里跳出来。
- **`data-code-theme` 的 6 套主题原来只写 6 个令牌**，缺的会回落到浅色 github 值 ——
  选 Monokai 时大部分 token 是粉绿黄、少数几个仍是 `#0550ae` 深蓝，压在 `#272822` 底上几乎读不出来。
  现在每套都写全 9 个。

### 怎么验的

- `_csscheck.mjs` 加了 14 条**计算值**断言：先确认 class 落在正确的 token 上（`codeTypeText === 'void'`），
  再确认它真有独立颜色。只量颜色不量文本是不够的 —— 选择器写错时 `querySelector` 会命中别的元素，
  颜色照样是「某个非默认值」，检查还是绿的。
- 亮线那条是**反向**断言：`::before` 的 `content` 计算值必须是 `none`（有亮线时是 `""`）。
- 两条都做过故意破坏，确认会红。
- 库里真实代码的围栏语言覆盖从 **34/41** 提到 **36/41**，剩下 5 个是有意豁免（`mermaid` 走图表渲染器、
  `redis` 在 highlight.js 里根本没有语法、`conf` 那三块实际是 Redis 配置映射到 nginx 会着色错、
  `mat` 是 JVM 参数、`asm` 只 1 块而 x86asm 模块 21 KB 不划算）。

## 14. 三个宿主，同一副版面

正文有三处渲染入口：门户**阅读页**、公开**分享页**、后台编辑器**预览**。
样式表早就是一份（`markdown.css` 用 `:is(.md-markdown, .md-ws__editor .markdown-body)`
把两套作用域并进同一个选择器），所以「改了一处、另一处还是老样子」这类漂移本来不该再有。

**但把同一份样例分别塞进三个真实宿主外壳量一遍，还是查出了两处不一致。**
量法是 `.verify/md/_hosts.mjs`：加载 `front/dist/assets/` 里**真实的构建产物 CSS**、
跑**真实的增强脚本**，再把 70 项计算值与 15 项结构计数读回来做三列对照。
（用源码拼外壳是不行的：bytemd 自带的那份 CSS 落在哪个 chunk、`@import` 怎么展开，
只有产物里才看得见。）

### 第一处：预览区不是成品

`enhanceMarkdown.ts` 有两个入口，后台预览走的是精简版 `enhancePreview` ——
只做标记 / 表格 / 图表 / 灯箱，把 Admonition、代码块工具条、公式当成「预览区里的多余改动」省掉了。

代价是预览不再等于成品：

| | 阅读页 / 分享页 | 后台预览（改前） |
| --- | --- | --- |
| `> [!WARNING]` | 琥珀色提示块 | **裸文本 `[!WARNING]`** |
| `$x^2$` | KaTeX 排版 | **裸美元符号** |
| 代码块 | mac 圆点 + 语言名 + 复制按钮 | 裸 `pre` |

预览的全部意义就是「看到读者会看到的东西」，省掉的恰恰是它唯一该做的事。
两个入口还天然会漂移：样式表改一处、另一个入口忘了跟，界面上就一半新一半旧 ——
和 §12 里 `==高亮==` 那条是同一个道理，只是这次不再「两个入口都挂」，而是**只留一个入口**。

现在三个宿主都调 `enhanceMarkdown`，`enhancePreview` 这个名字被删掉。

### 第二处：阅读字体的作用范围只写了分享页

`--md-read-font` / `--md-read-scale` 写在根元素上，但消费方只有
`.md-reading[data-mode='share'] .md-markdown` —— 理由是「设置面板在哪，作用范围就该在哪」。

**面板只是个入口，它写的是一个设备偏好。** 读者在分享页选了霞鹜文楷，回头读门户、
作者在后台预览，看到的都该是同一张版面；只给一处，另两处就成了「同一篇文档换个入口换一副样子」，
比没有这个设置更让人困惑 —— 读者分不清是字体没生效还是文档本来就这样。
消费方改成 `:is(.md-markdown, .md-ws__editor .markdown-body)`。

**字号与行高必须成对地用 `--md-read-scale` 补偿**（见 §11）：只换字族的话，
楷体的字面只占 em 的 87%、系统字体占 94%，字看着小而空，读者只会觉得「换了楷体行距就变大」。
字号乘它、行高除以它，两者相乘不变 —— **行盒高度一点没动**。

**正文宽度（`readerWidth.ts`）没有跟着放开**，仍只有分享页。那是「这一栏多宽」，
门户阅读页的栏宽由两侧拖拽手柄决定，和「按百分比收窄并居中」不是一回事。
同一个词在两处指的是两样东西，别因为名字像就一起放开。

### 第三处：入口也只在分享页

把作用范围放开之后还漏了一步：**读者没地方改它**。面板（`ShareSettingsMenu.vue`）早先只挂在
分享页顶栏，门户阅读页翻遍顶栏也找不到。偏好在三个宿主都生效，却只有一个入口 ——
这比没有这个设置更让人困惑。

现在是同一个组件（`ReaderPrefsMenu.vue`）挂两处：分享页顶栏（`ShareTopBar.vue`）与
门户阅读条（`ReadBody.vue`，`v-if="!isShare"` 避免分享页出现两颗）。用 `context` 区分宿主，
差异只有两处：提示语那句（分享页说「只作用于这份分享」），以及**正文宽度那一行只在分享页渲染**
—— 门户那一栏没有百分比可调。

**面板 `Teleport` 到 `body`**：触发按钮所在的顶栏与阅读条都是 sticky 且带 `backdrop-filter`，
按规范那会给 `fixed` 后代创建包含块，按视口坐标算出来的 `left/top` 会跟着偏移。
分享页那条通栏宽又吸附在视口顶端，两个方向偏移恰好都是 0，所以旧代码看着没问题；
门户阅读条只是中间一栏，同一套算法直接错位。`_prefscheck.mjs` 里放了一颗**不** Teleport 的
对照组量这个偏移（实测水平偏 400px，正是左栏宽度）—— 既证明这一步是必要的，
也证明那份检查真的能失败。

### 怎么验的

- `_hosts.mjs` 要求三个宿主的 **15 项结构计数**与 **70 项计算值逐项相同**，亮暗两轮。
- **阅读字体的作用范围**：注入哨兵字族 `SentinelReadFont` + `scale 1.1`，量正文容器自己的
  `font-family` 计算值。只读 `var(--md-read-font)` 是没用的 —— 变量写在根元素上，
  三个宿主都「有」它，读变量永远读得到，验不出消费方认不认。
  顺带验补偿：字号该变 17.05px，行高仍是 27.9px（行盒不动）。
- **检查必须能失败**：另跑一份「改前脚本」（`_enhance-before.js`）作差分，
  要求结构**明确不同**（实测 10 项）。否则一个永远说「一致」的检查，
  在改动完全没生效时也是绿的 —— 这个坑在 §13 已经踩过一次。
- 全量流水线跑完这份样例 **35–48 ms**（预览区每轮重渲染都要跑一遍，这个量级可以接受）。

## 15. 阅读主题包：换的是令牌，不是样式表

读者想要的不止是明 / 暗两档，而是「像 Typora 的紫笺」「像 VitePress 的青提」这种整篇气质。
如果每套主题都写一份 CSS，代价是：改一次正文结构要同步改六份，漏一份就漂移（§14 同一个病）；
而且主题只能随前端发版，管理员装不了。

所以主题包被定义为**一组同名 CSS 自定义属性的取值**，消费方仍是那唯一一份 `markdown.css`：

| 方案 | 结构跟着正文走 | 管理员可装 | 能注入选择器 / 脚本 |
| --- | --- | --- | --- |
| 每套主题一份 CSS | ✗ 六份手工同步 | ✗ 要重新构建 | ✗ 风险大 |
| **JSON 令牌包（现在）** | ✓ 只有一份消费方 | ✓ 上传即生效 | ✓ 值级白名单挡掉 |

安全边界因此变成「值」而不是「代码」：`url()`、`@import`、`!important`、分号花括号一律拒绝，
能改的只有颜色、字体栈、渐变与尺寸。前后端各校验一遍，绕过界面直接调接口也过不了后端。

### 默认主题也在磁盘上

`default`（澄澈）曾经是不落盘的占位主题，直接复用 `variables.css` 的基线。现在它和其余内置主题
一样是一份 JSON（`default.json`），区别只有两点：id 保留、不能上传同名包；没有编辑入口，
所以只要它还在磁盘上，启动时就按程序内的版本刷新，升级换肤不会卡在旧配色。

它同样可以卸载：卸载只删 `.json`、保留种子标记，重启不会复活；读者回落到 `variables.css`
的基线样式，「恢复内置主题」能把它再写回来。其余内置主题走同一套「种子 → 可卸载 → 可恢复」。

### 代码高亮为什么要单独的开关

主题包里的 `--md-tk-*` 如果直接写在 `body` 上，会**按继承**盖掉读者在账号设置里选的 GitHub / Monokai ——
自定义属性不靠选择器优先级竞争，靠「离元素更近」。所以代码令牌单列一组，选择器多带
`html[data-code-theme='theme']` 前提；默认值也从 `github` 改成 `theme`（跟随阅读主题），
显式选过代码主题的人不受影响。

### 字号是独立的一根轴

主题管「字看起来是什么气质」，字号管「这一屏放多少字」，两者正交。
字号存 `--md-read-size`（13–22px，步长 0.5），代码块 / 表格 / 脚注按各自比例
`calc(var(--md-read-size) * 0.87)` 派生 —— 只缩放正文会让代码块在 22px 下显得格外小。
它与 §11 的 `--md-read-scale` 相乘：scale 补偿字体字面差异（行盒不动），size 是读者主动调的那一档。

### 面板放不下之后

主题卡片 + 外观 + 字号 + 字体 + 宽度已经超过一屏，面板因此给了
`max-height: min(78vh, 640px)` 与内部滚动；`place()` 再把 top 夹在视口内。
不做折叠：读者点开面板就是来逐项挑的，藏起来只会多一次点击。

## 16. 邮箱验证：闸门放在进门处，不放在写作中间

### 建号之后停在「去收邮件」，不再自动登录

注册原本的成功动作是「拿同一组凭据顺手登录一次」。站点要求验证时这条路必然被闸门挡下，
所以注册页改停在一段说明上：账号已经有了，缺的只是邮箱里那一下。继续走自动登录，用户
看到的是一条 40302 报错，读起来像「注册失败」，于是再注册一次、撞上「用户名已被占用」。

判据只看后端回吐的 `emailVerified`，不拿站点配置自己猜 —— 猜错就会出现「页面让人等邮件，
后端其实已经放行」。

### 闸门只放在登录

正在写作的人不该被中途打断；能进来的人一律放进来，只提醒一次（管理台那句「补验证邮箱」
弹窗，关掉就不再纠缠）。平台 ADMIN 豁免是同一件事的另一面：管理员把 SMTP 改坏时，手上
只剩「关掉开关」这把钥匙，如果连管理员都卡住，自部署者就只能进数据库改那一列。

### 发不出去就当作已验证

没配邮件服务、发信失败、口令解不开 —— 这三种情况注册照旧放行。邮件服务是第三方，
不能因为它不可用就把人永久关在门外，也不能让「开关已打开」变成一条说谎的文案：
回给前端的因此是「开关 ∧ 传输可用」的生效值，而不是管理员存下的那个开关。

### 令牌提交用 POST

落地页 `/verify-email?token=` 由 SPA 承接，页面自己不发 GET。邮件安全扫描器会预取链接
指向的地址，GET 一次等于替用户把一次性令牌用掉，等他真点开时只剩「链接无效」。同理，
令牌只在这一次请求里出现，不进本地存储、不进日志。

### 落地页不借管理端外壳

它由一个零登录态的收件人点开，只有一个结论要说（成功 / 失败），为此加载 Element Plus
不划算。于是复用阅读端的 `.md-state` / `.md-lock` 骨架，路由不带 `meta.admin`，chunk 里
只有视图自己。

### 口令的回显只说「已设置」

SMTP 口令永远不回明文，输入框占位是「已配置，留空则不修改」。留空和清空是两种语义，
所以清除必须显式发一个标记位而不是空串 —— 空串在这个接口里已经是「沿用」了。
