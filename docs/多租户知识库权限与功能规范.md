## 1. 模型总览

```
用户 (users)
 ├─ platform_role = ADMIN（平台超级管理员，内置引导账号） | USER（普通用户）
 ├─ 个人组织：注册时自动创建，type=PERSONAL，本人唯一 OWNER，不可被申请加入
 └─ 团队组织：可属于多个（tenant_member 一人多行），加入需组织管理员审批

组织 (tenant, type=TEAM|PERSONAL)
 ├─ tenant_member.role = OWNER | ADMIN | MEMBER
 ├─ tenant_join_request：申请-审批流水
 └─ 知识库 (knowledge_base) 归属唯一组织，slug 仅在组织内唯一

知识库
 ├─ visibility     = public | org | private        ← 决定「谁能读」
 ├─ maintain_scope = owner_only | members | org_all ← 决定「谁能写」
 └─ kb_member(kb_id,user_id,role)                   ← 逐人维护名单
```

**两轴正交**是本次设计的核心：可见性与维护权各自独立设置，可表达「全组织可读、只给这 3 个人改」这类真实诉求。

### 1.1 关键不变式

| # | 不变式 | 实施位置 |
|---|---|---|
| I1 | 每个 TEAM 组织至少 1 个 OWNER；最后一个 OWNER 不可降级 / 退出 / 被移除 | `TenantMemberService` |
| I2 | 内置平台管理员不可禁用 / 降级 / 删除 | 保留 `UserAdminService.java:82,97,120` |
| I3 | 个人组织不可被申请加入、不出现在组织发现列表、不可删除；其 `status` 恒为 `active`（账号可用性只看 `users.status`） | 查询层过滤 `type='PERSONAL'` |
| I4 | `storage_key` 一经创建永不可变；改名只改 `name`，slug 变更只改 URL 不动目录 | `VaultFileService` |
| I5 | 成员被移出组织 / 撤销维护权，下一次请求即刻生效（不做 token 吊销） | 依赖 `AuthInterceptor.java:50` 每请求回读 |
| I6 | 用户被删除时，其创建的组织须先转让 OWNER，否则禁止删除 | `UserAdminService` 扩展 |
| I7 | 平台超管 bypass 一律写 `audit_log`，且默认不注入 `tenant_member` 关系 | `AccessService` |

> **I7 的留痕口径（M2 实施补充）**：只有「本来不行、靠超管身份才放行」的动作才记 ——
> 判定前先用普通成员身份重算一次，仍然通过就不写。因此超管读他人的 `org`/`private` 库**会**留痕，
> 读 `public` 库与操作自己个人组织的库**不会**。`require*` 才写审计，`can*` 与列表用的
> `applyVisibleScope` 一律不写：否则搜索框逐字符联想会把流水刷满。
> 由 `AccessServiceTest$SuperAdmin` 四向守住（越权写/越权读留痕、常规流量与列表不留痕）。

### 1.2 「组织管理员可写一切」是刻意为之

`maintain_scope=owner_only` 时，组织 OWNER/ADMIN **仍然可写**该组织的库。这不是漏洞：管理员被赋予治理职责，若不允许其处置失控内容，该设置就退化成「对管理员保密」，而这不是本产品要提供的能力。

**需要绝对私密的库，请放在个人组织里**（个人组织没有第二个成员）。这是个人组织存在的唯一理由，也是 I3 的配套说明。

## 2. 权限裁决

### 2.1 动作枚举

```java
public enum KbAction {
    KB_VIEW, KB_CREATE, KB_EDIT_META, KB_SET_VISIBILITY, KB_DELETE,
    KB_MEMBER_MANAGE, DOC_READ, DOC_WRITE, DOC_RENAME, DOC_MOVE,
    DOC_DELETE, DOC_UPLOAD_ASSET, DOC_IMPORT,
    SHARE_CREATE, SHARE_REVOKE, SHARE_VIEW_STATS,
    TENANT_RENAME, TENANT_DELETE, TENANT_MEMBER_MANAGE, TENANT_JOIN_REVIEW, AUDIT_READ
}
```

### 2.2 读权限（`visibility` 轴）

对知识库 `kb` 与访问者 `u`，`KB_VIEW | DOC_READ` 成立当且仅当：

1. `u` 是平台超管 → **是**（记 audit，I7）
2. `kb.visibility='public'` → **是**（含匿名游客）
3. `kb.visibility='org'` 且 `u` 是 `kb.tenant_id` 的活跃成员 → **是**
4. `kb.visibility='private'` 且满足以下任一 → **是**
   - `u.id == kb.created_by` **且为该组织活跃成员**
   - `u` 在该库 `kb_member` 名单中（任意 role）**且为该组织活跃成员**
   - `u` 在该组织中为 `OWNER` 或 `ADMIN`
5. 否则 → **否**

`visibility='org'` 是新的默认值（老数据 `private` → `private`，`public` → `public`，见 §7）。

> **实施补充（M2）**：以上判定有一条前置条件 —— 库所属组织必须存在且 `status='active'`。
> 组织被封禁即整库冻结，`public` 也一并下线：责任主体还在，内容先不出门。
> 列表用的 `applyVisibleScope` 与逐条的 `canRead` 必须同口径，否则会出现「首页看得见、点进去 404」。
> 该规则由 `AccessServiceTest$VisibleScope` 与 `$ReadAxis.disabledTenantRevokesMembership` 守住。

> **实施补充（M3）—— `created_by` 同样只在组织内有效**：第 4 条的创建者分支额外要求「活跃成员」，与名单同口径。
> 否则「退出或被移出组织」只删得掉成员行，删不掉 `created_by` 赋予的读写与治理 —— 那是比名单残留更大的一条
> 后门（前创建者仍可 `KB_DELETE` 整个库）。代价是：**人离开组织即失去他在那里建的库，库留在组织**。
> 个人组织永远只有本人，且本人恒为 OWNER，所以这条对个人库无任何影响。
> 由 `AccessServiceTest$Governance.creatorLeavingOrgLosesOwnKb` 与 `$VisibleScope.creatorLeavingOrgDropsOwnKbFromList`
> （后者保证列表 SQL 与逐条判定不给出口径差）守住。

### 2.3 写权限（`maintain_scope` 轴）

`DOC_WRITE | DOC_RENAME | DOC_MOVE | DOC_DELETE | DOC_UPLOAD_ASSET | DOC_IMPORT | KB_EDIT_META` 成立当且仅当：

1. `u` 是平台超管 → **是**
2. `u` 在该组织中为 `OWNER` 或 `ADMIN` → **是**
3. `u.id == kb.created_by` **且为该组织活跃成员** → **是**
4. `maintain_scope='members'` 且 `u` 在 `kb_member` 中 `role='EDITOR'` → **是**
5. `maintain_scope='org_all'` 且 `u` 为该组织活跃成员 → **是**
6. `maintain_scope='owner_only'` → **否**（已由 2、3 覆盖）
7. `u` 未登录 → **否**

> **实施补充（M2）**：
> - 第 4、5 条额外要求「先过读轴」。`private` + `org_all` 这类自相矛盾的配置不授予写：
>   普通成员读不到该库，就不该能往里写。组织停用时同上，第 1~5 条一律不成立（超管除外）。
> - 第 4、5 条都以**该组织活跃成员**为前提。名单是组织内做加法的工具，不是跨组织通道（§9）：
>   把组织外的人写进 `kb_member` 不产生任何权利，移出组织后残留的名单行也立即失效。
>   要与人协作，正确动作是把他拉进组织 —— 这也让「撤销一个人的访问权」只有一处可做（成员管理）。
> - 未知 `maintain_scope` 值按 `owner_only` 处理（fail closed），不会因为「不是 owner_only」就放行。

### 2.4 治理动作

| 动作 | 允许者 |
|---|---|
| `KB_CREATE` | 组织内 `MEMBER` 及以上（个人组织恒为其 OWNER） |
| `KB_DELETE` | 平台超管、组织 `OWNER`/`ADMIN`、`created_by` |
| `KB_SET_VISIBILITY` | 平台超管、组织 `OWNER`/`ADMIN`、`created_by` |
| `KB_MEMBER_MANAGE` | 平台超管、组织 `OWNER`/`ADMIN`、`created_by` |
| `SHARE_CREATE` | 具备写权限者 |
| `SHARE_UPDATE` | 平台超管、组织 `OWNER`/`ADMIN`、该分享 `created_by` |
| `SHARE_REVOKE` | 平台超管、组织 `OWNER`/`ADMIN`、该分享 `created_by` |
| `SHARE_VIEW_STATS` | 组织 `OWNER`/`ADMIN`、`created_by` |
| `TENANT_RENAME` | 组织 `OWNER` |
| `TENANT_DELETE` | 组织 `OWNER`；个人组织禁止（I3） |
| `TENANT_MEMBER_MANAGE` | 组织 `OWNER`/`ADMIN` |
| `TENANT_JOIN_REVIEW` | 组织 `OWNER`/`ADMIN` |
| `AUDIT_READ` | 组织 `OWNER`/`ADMIN`、平台超管 |

> 注：组织 `ADMIN` **不能管理 `OWNER` 的角色、不能移除 `OWNER`**（仅 OWNER 可转让与任免）。`ADMIN` 也不能删除组织。

> **实施补充（M2）**：
> - `SHARE_UPDATE` 与 `SHARE_REVOKE` 同档（改密码 / 改有效期等于能撤，权限不得高于撤销）。
> - 分享的唯一性目标是**库 + 目标路径**（`uk_shares_target`），与创建者无关：一个库的一篇文档只有一条有效链接。
>   因此 `SHARE_CREATE` 命中已有链接时是「更新那条链接」还是「另建一条」必须由产品确认，但**不能**按创建者查
>   —— 否则第二个维护者会撞唯一键，或悄悄复活他人撤销过的链接。见 `ShareServiceImpl.createOrUpdate`。
> - `owner_id` 在 `shares` 上退为「谁建的这条」审计字段，撤销权判定看它，不看库的创建者。
>
> **实施补充（M3）**：
> - 表中所有 `created_by` 分支（`KB_DELETE` / `KB_SET_VISIBILITY` / `KB_MEMBER_MANAGE`）都以**该组织活跃成员**为前提，
>   理由见 §2.2 的 M3 补充。组织 `OWNER`/`ADMIN` 档位本身已含成员身份（角色行就在 `tenant_member` 上）。
> - 组织轴动作（`TENANT_VIEW` / `TENANT_RENAME` / `TENANT_MEMBER_MANAGE` …）只能经 `canInTenant` / `requireTenant`
>   判定；`can(kb, …)` 收到组织轴动作一律返回 false，避免出现「借某个库的入口放行整个组织」的旁路。

### 2.5 拒绝时的 HTTP 语义

沿用现有「不泄露存在性」约定（`docs:1118`）：

| 情形 | 响应 |
|---|---|
| 未登录访问受限资源 | `401 / 40100` |
| 已登录但无读权限（`KB_VIEW`/`DOC_READ` 不成立） | **`404 / 40400`**（与「不存在」不可区分） |
| 有读权限但无写/治理权限 | `403 / 40300` |
| 非成员访问整个组织上下文 `/console/{org}/**` | **`404 / 40400`** |
| 越权转让 / 最后一个 OWNER 降级 | `403 / 40300`，message 说明原因 |
| 编辑锁被他人持有 | `409 / 40902`（新增码，携带持有者信息） |
| 保存基线不一致 | `412 / 41200`（新增码） |

`ErrorCode` 需新增：`DOC_LOCKED(40902)`、`STALE_WRITE(41200)`、`JOIN_REQUEST_PENDING(40903)`。

> **实施补充（M2）**：`requireTenant` 分两步判，是为了让上表的第 3、4 行真的能区分开 ——
> 先判「是不是这个组织的人」，不是则 `404`（连组织存在性都不确认）；是成员但动作不够则 `403`。
> 合成一步会让普通成员在 `TENANT_DELETE` 上收到 `404`，误以为组织被删了。
> 停用的组织同理：`requireTenant` / `requireKb` 一律按「不存在」处理，超管例外。

> **实施补充（M3）—— 「非成员 404」没有例外**：组织详情页 `GET /api/console/{org}`（动作 `TENANT_VIEW`）也要成员身份，
> `discoverable` **不**给它开后门。陌生人能看到的组织信息只从 `GET /api/tenants/discover` 这一个专用查询出口出去
> （`type='TEAM' AND discoverable=1 AND status='active'`，字段白名单：名称 / slug / 简介 / 头像 / 成员数 / 公开库数）。
> 这样「可被发现」与「组织上下文」两条路径各自只有一处判定，不需要在 `AccessService` 里维护第二套可见性规则。
> 相应地 `TENANT_VIEW` 归在 `Axis.TENANT_MEMBER`（与 `KB_CREATE` 同档），而不是单开一个轴 —— 单开一个轴却没有任何
> 调用者需要区分它，只会多一条永远走不到的分支。

### 2.6 唯一裁决入口

全部判定收敛到一个无状态服务，禁止任何旁路 `if`：

```java
public interface AccessService {
    boolean canRead(KnowledgeBase kb, LoginUser u);
    boolean can(KnowledgeBase kb, LoginUser u, KbAction action);
    boolean canInTenant(Tenant tenant, LoginUser u, KbAction action);
    KnowledgeBase requireKb(Long kbId, KbAction action, LoginUser u);  // 失败按 §2.5 抛 BizException
    Tenant requireTenant(Tenant tenant, KbAction action, LoginUser u);
    Share requireShare(Share share, KbAction action, LoginUser u);
    /** 把可见集条件加到查询上：列表 / 搜索 / 统计的唯一读出口 */
    void applyVisibleScope(LambdaQueryWrapper<KnowledgeBase> wrapper, LoginUser u, Long tenantId);
    /** 「我参与的库」，列表筛选项；必须与 applyVisibleScope 取交集，单独使用不产生权限含义 */
    void applyParticipatingScope(LambdaQueryWrapper<KnowledgeBase> wrapper, LoginUser u);
}
```

`can*` 是纯判定（无副作用、不写审计），`require*` 才留痕并抛错 —— 这样同一条判定可以在
列表 SQL 与单条校验里复用而不产生两份口径。

**守门测试**（`AuthorizationGuardrailTest`，不启动容器，直接扫 `src/main/java`）：

| 规则 | 断言 |
|---|---|
| 角色 / 组织形态字面量（`"OWNER"`、`"ADMIN"`、`"PERSONAL"`…） | 只允许出现在实体常量声明处与 `permission/` 包 |
| 拿 `owner_id` 当权限用（`getOwnerId()` 比较、`eq(*::getOwnerId, …)`） | 除许可清单外为零；清单按**代码片段**而非按文件放行，同文件新增一处即变红 |
| 已删除的绕过入口 `requireOwned` / `requireReadable` | 不得复活 |
| 扫描器自检 | 源码根下 java 文件数 > 50，避免路径写错导致守门测试静默空跑 |

许可清单现存 4 条，全部是数据清理或展示（注销用户连带清库、管理台库数量列、撤销用户分享、
「我创建的分享」列表筛选），M5 分享转组织维度后可删除其中一条。

## 3. 组织与成员

### 3.1 注册与个人组织

- `register-enabled` 默认值由 `false` 改为 **`true`**（`application.yml:72`）。
- 注册成功即 `status='active'`，可直接登录，**不再进入平台待审核队列**（改动 `AuthServiceImpl.java:88-89`）。
- 注册事务内同步创建：个人组织（`type='PERSONAL'`、`slug='u-'+username`、`name=displayName`）+ 一条 `tenant_member(role='OWNER')`。
- 历史 `status='pending'/'rejected'` 行继续被 `AuthInterceptor.java:54-56` 拒绝，由平台超管在平台后台处置 —— 向后兼容，不批量改数据。

### 3.2 slug 命名空间

| 对象 | 唯一性 | 规则 |
|---|---|---|
| 组织 slug | **全局唯一** | 复用 `SlugUtil.slugify`；保留字表（`SlugUtil.java:11-14`）新增 `w`、`api`、`share`、`kb`、`admin`、`platform`、`u` |
| 个人组织 slug | 全局唯一 | `u-{username}`，用户改名不联动 |
| 知识库 slug | **组织内唯一** `uk(tenant_id, slug)` | 从全局唯一降级，见 §7 链接兼容 |
| `storage_key` | 全局唯一，永不可变 | `o{tenantId}/{kbSlug}`，即磁盘目录 `vaults/o3/面试手册/` |

### 3.3 加入流程

```
发现组织（type=TEAM 且允许被发现）
   → POST /api/console/{org}/join-request   {message}
   → 状态 pending，写入 tenant_join_request
   → 组织 OWNER/ADMIN 在「入组申请」页审批
        ├─ 批准 → 插入 tenant_member(MEMBER)，请求置 approved
        └─ 拒绝 → 置 rejected（同一 (tenant,user) 再次申请复用该行，重置为 pending）
   → 已是成员再申请 → 409 JOIN_REQUEST_PENDING 或直接 40900
```

组织管理员也可**直接添加成员**（`TENANT_MEMBER_MANAGE`），跳过申请流。

`tenant.join_policy ∈ {request, invite_only}`：`invite_only` 时不开放申请入口。

> **实施补充（M3）—— 申请入口是 `/console/{org}/**` 成员门的唯一例外**：`POST /api/console/{org}/join-request` 的发起者
> 按定义还不是成员，若让 `TenantInterceptor` 按 §3.4 一律拦成 404，加入流程就没有入口了。落地口径：
> 该端点走 `tenantIdBySlug` + `Tenant.isPublicProfile()`（TEAM + 可被发现 + 活跃）判定，
> 不走 `requireTenant`；其余 `/console/{org}/**` 一律成员门。也就是说 `isPublicProfile()` 的读者只有两处 ——
> 发现列表与申请入口，两处都是「不确认私有组织存在」的语义。

### 3.4 组织上下文与 URL

组织上下文**只从路径解析**，不依赖 localStorage / Pinia 持久态 —— 刷新、收藏、多标签页同时开两个组织都不会串。

> **全站部署前缀 `/minidocs`**：后端 `server.servlet.context-path=/minidocs`（`CONTEXT_PATH` 可覆盖），前端
> Vite `base` 与 vue-router `base` 与之一致。下面列出的都是**前缀之后**的 context-relative 路径；
> 浏览器实际访问 `域名:端口/minidocs/...`。后端生成给浏览器直接请求的绝对地址（资源前缀、文档前缀、
> 头像、分享链接）统一经 `common/web/AppPaths` 补前缀，别在业务代码里手写 `/minidocs`。

```
/console/{orgSlug}/**                组织内（需成员身份，TenantInterceptor 裁决）
/console/{orgSlug}/kbs/**            组织知识库管理（原 admin 侧能力）
/console/{orgSlug}/settings/**       组织设置 / 成员 / 入组申请 / 审计
/platform/**                   平台超管后台（原 /api/admin 对应页面）
/kb/{orgSlug}/{kbSlug}         登录态阅读页
/share/{token}                 分享页（不变）
/login /register               认证
```

`GET /api/me` 返回 `tenants[]`（含 role）与 `lastTenantSlug`，供前端顶栏渲染组织切换器；`lastTenantSlug` 存 `user_settings`，仅作为登录后的默认落地页，不作为权限依据。

> **实施补充（M3）**：`lastTenantSlug` 的写入复用 `PUT /api/settings` 的浅合并（`user_settings` 无键白名单，
> 少一条只为一枚字段而生的接口），读取集中在 `GET /api/me` 一处，且**只在该组织仍在 `tenants[]` 里时才回传**，
> 否则回 `null` —— 成员身份会变，落地点不该指向一个 404；前端把 `null` 当作「回落到 `tenants[0]`」的信号。
> `tenants[]` 的顺序是固定的：个人组织置顶、其余按 slug 字典序，切换器不会因为刷新而重排。
> `GET /api/auth/me` 保持不变：它只管登录态，组织上下文一律经 `/api/me`。

### 4.3 文档与编辑锁

```
GET    .../kbs/{slug}/tree
GET    .../kbs/{slug}/doc?path=            响应头带 X-Base-Mtime / X-Base-Size
GET    .../kbs/{slug}/render?path=
PUT    .../kbs/{slug}/doc?path=            body 带 baseMtime/baseSize；无有效锁 → 403；基线不符 → 412
POST   .../kbs/{slug}/lock?path=           获取或续期（幂等）；被他人持有 → 409 + {holder, nickname, acquiredAt}
DELETE .../kbs/{slug}/lock?path=           释放（持有者本人，或具 KB_MEMBER_MANAGE 权者强制解锁）
POST   .../kbs/{slug}/doc/rename|move|delete
POST   .../kbs/{slug}/upload|import
```

锁设计（分工式，单实例无 Redis，`docs:891` 约束保留）：

- 状态落 **DB 而非 Caffeine**：进程重启丢锁会让两人同时进编辑，正是要消灭的问题；顺带提供审计。
- TTL 60s，编辑器每 20s 心跳续期；`beforeunload`/`visibilitychange` 用 `fetch(..., {keepalive: true})` 主动释放（见下方实施补充）。
- 409 时编辑器**降级只读**并显示「X 正在编辑 · N 秒前」，每 10s 轮询，锁释放后自动恢复可编辑。
- 保存基线用 `size + modifiedAt`（`DocContentVO` 已回传，客户端手里就有，无需新协议）。
- 不做历史版本、不做回收站、不做内容 diff 合并（维持 `docs:37`）；冲突只提示不自动合并。

> **实施补充（M4）**：
> - **`X-Base-Mtime` / `X-Base-Size` 响应头不做**。`DocContentVO` 已经把 `size` / `modifiedAt` 放在响应体里
>   （§4.3 自己那句「客户端手里就有，无需新协议」），再开一条头通道只会让两处取值随时间漂移。
>   恢复上下文统一走响应体：`BizException` 现在带一个 `payload`，由 `GlobalExceptionHandler` 放进
>   `ApiResponse.data`，因此 409 带回 `LockVO`（持有者 id / 用户名 / 展示名 / acquiredAt / expiresAt），
>   412 带回磁盘当前的 `{baseSize, baseMtime}`，文档已被删除时带回 `{missing: true}`。
> - **基线两列都要给，缺任一列按 412 处理而不是 400**：编辑器刷新一次即拿到新基线，缺列只可能是
>   「拿的是别处读的旧值」，此时最该发生的动作是重新载入。时间**比到秒为止** —— `modifiedAt` 经
>   JSON 往返（ISO 文本，秒为 0 时省略秒位）纳秒位必然丢失，比到纳秒会让正常保存随机失败。
> - **锁的读门与写门分开**：`POST .../lock` 走 `DOC_WRITE`（拿不到写权的人不该能占锁），
>   `GET` / `DELETE .../lock` 走 `DOC_READ`（看锁与释放锁不是写动作；释放他人锁额外要
>   `KB_MEMBER_MANAGE`，并写一条 `op=forceUnlock` 审计）。过期锁不删除，由下一个获取者
>   带条件 `UPDATE` 就地接管，因此不需要清理任务；并发一律靠条件更新的影响行数裁决，不先读后写。
> - **路由仍是 `/api/kbs/{kbId}/lock`**（按 id），§4.3 的 `{slug}` 形式与 `/api/console/{org}/**` 前缀一起等 M5。
> - **审计读取端点已在 M4 落地**：`GET /api/console/{org}/audit?action=&page=&size=`，走
>   `requireTenant(AUDIT_READ)`，非成员 404、成员不足 403；只出本组织，`tenantId` 缺失时返回空页
>   而不是全表。保留期由 `AuditRetentionTask` 每天 03:30 清理 180 天前的条目。除 §4.3 已列的动作外，
>   M4 还补上了改 `visibility`、改维护档位、名单授予/撤销、删库、分享创建/更新/撤销这几处写入点。
> - **审计 `detail` 只放定位信息，绝不放正文、token 与密码哈希**；分享相关条目记 `shareId` 而不记
>   token —— 审计页能读到的东西不该比公开链接能打开的更多。删库时把 `name/slug/storageKey` 钉进
>   `detail`，因为那条 `kb_id` 从此指向空行。
> - **编辑器只读降级走 CodeMirror 实例，不走 bytemd 属性**：这一版 `@bytemd/vue-next` 的 `editorConfig`
>   只在初始化时生效、`mode` 没有 read-only 取值，因此拿 `.CodeMirror` 元素上的 CM5 实例
>   `setOption('readOnly', 'nocursor')`。锁状态未知（刚打开、请求在飞）时**不**置只读，否则每次切文档
>   都会灰一下，看起来像被别人锁住了。
> - **412 冲突不写 localStorage**：弹窗把「我的版本」送进剪贴板后重新载入最新版，两版都不丢，
>   也不必给前端造一套草稿存储。自动保存撞上 412 时只提示、不弹模态（后台任务不该抢焦点）。
> - **卸载释放锁用 `fetch(..., {keepalive: true})` 而不是 `sendBeacon`**：`sendBeacon` 带不上
>   `Authorization` 头。轮询与释放都走 `silentError`，否则网络抖动会每 10s 刷一次吐司。

## 7. 迁移与兼容

### 7.0 expand / contract 两步（已实施）

迁移拆成 **V2 扩展 + V3 收缩**，且 V3 必须与「会写新列的代码」同批发布：

- **V2**：建 6 张新表、给 `knowledge_base` 加 3 个**可空**列、回填个人组织与成员行。只增不删，v1 代码照常可跑。
- **V3**：重跑回填做兜底，然后收紧 `NOT NULL`、把 `uk_kb_slug` 换成 `uk(tenant_id, slug)`、换 `shares` 唯一索引（SQLite 走 create-copy-drop-rename 重建表）。

> 拆分原因（实测踩过）：把「建表+回填」和「收紧约束+换索引」塞进同一个脚本，收缩后的 schema 会跑在
> 还不写 `tenant_id` 的 v1 实体上，插入直接 `NOT NULL constraint failed` —— 中间态不可部署。

### 7.1 回填规则

1. **每个既有用户一个 PERSONAL 组织**（`slug='u-'||LOWER(username)`、`join_policy='invite_only'`、
   `discoverable=0`），并把其名下库挂进去；owner 已注销的孤儿库落到 `u-deleted-{owner_id}`（`status='disabled'`），
   保证不丢目录。**不为内置管理员建 `slug='system'` 的特殊 TEAM 组织** —— 超管的跨租户能力由 `AccessService`
   bypass 提供，与属于哪个组织无关（§2.4）；建一个「系统组织」只会让归属规则多出一条特例。
   - **个人组织的 `status` 恒为 `active`，不跟随 `users.status`**：账号是否可用只在 `users` 上表达一次。
     若迁移把 `pending` 抄进 `tenant.status`，「审批通过」就得同时改两处，漏一条路径即出现
     「用户已放行却看不见自己的库」这种静默失效。`tenant.status` 只对 TEAM 组织有意义（平台侧封禁）。
   - `u-` 前缀为个人组织保留：M3 建 TEAM 组织时须拒绝该前缀，否则用户名 `alice` 的个人组织会被抢注。
   - 注册路径（`AuthServiceImpl.register`）与内置管理员引导（`AdminInitializer`）都在建用户后立即
     `ensurePersonalTenant`；`kbService.create()` 内仍保留惰性创建，兜住迁移之后未建过库的用户。
2. **`storage_key` 回填 + 磁盘搬迁**：`VaultDirectoryRelocator`（`InitializingBean`，`@DependsOn("dbMigrator")`）
   把 `vaults/{slug}` 移至 `vaults/o{tenantId}/{slug}`。
   - 放在 Bean 初始化阶段而非 `ApplicationRunner`：Web 容器在 refresh 收尾才启动，搬迁期间不可能有请求在读目录。
   - **搬迁就是 `Files.move`，不加 `.migrated` 标记**：目标已存在即视为已搬过，天然幂等、重启安全。
   - `storage_key` 缺失或形态非法 → `StorageKey.validate` 抛异常终止启动，绝不回退到 slug 定位。回退会把非法
     标识静默解析成另一个真实存在的目录，比停机危险得多；`DocCountCalibrationTask` 扫到空目录把 `doc_count`
     归零的假象由此挡掉。
   - `VaultFileService.rootOf/ensureRoot/deleteRoot` 一律收 `storage_key`，M1 已把 22 处调用点全部切换。
3. **老公开链接兼容**：`/kb/{oldSlug}` 全局唯一性已被降级为组织内唯一，因此：
   - 旧 slug 在库内唯一时 → `301` 到 `/kb/{orgSlug}/{kbSlug}`；
   - 多组织撞名时 → 落到一个消歧列表页（仅 public 库参与）。
   - 已外发的 `/share/{token}` 完全不受影响。
4. **`visibility='private'` 原值保留**，语义从「仅 owner」变为 §2.2 第 4 条（创建者 + 名单 + 组织 ADMIN/OWNER）。老数据无组织 ADMIN，故等价于「仅 owner」，行为不劣化。

## 11. 实施补充（M5）

M5（门户与分享租户化 + 单 SPA 合并 + 组织 UI）落地时新增的约定。只记规范正文里没有、
而读代码时必须要有的那些。

### 11.1 前端只有一个入口，深链接回退要显式枚举

- 构建产物只有一个 `index.html`（`front/` 一次构建直接写进 `backend/src/main/resources/static/`），
  门户 / 阅读 / 分享 / 登录注册 / `/console/**` 组织管理 / `/platform/**` 全在同一张路由表里。
- `SpaFallbackController` 把 `/`、`/kb/**`、`/share/**`、`/login`、`/register`、`/account`、`/discover`、
  `/console/**`、`/platform/**` forward 到 `/index.html`。**必须逐前缀枚举**：控制器映射优先级恒高于静态资源处理器，
  写成 `/**` 会把 `/assets/**` 一并吃掉，带 hash 的 JS/CSS 全变 404。新开顶层前缀才需要补一条，
  页面内部加路由不用动这里。**不要映射 `/index.html` 自身**——forward 会重入分发链路，自转发死循环。
- 组织段只在路径里（§3.4 的落地形式）：前端把 `org` 存进 pinia 只是给顶栏渲染用，
  **地址栏没有组织段时守卫会把上下文清空**（`admin/shell.ts`）。留着上一个组织的值，任何一次误用
  `orgPath()` 都会变成「人看着账号设置，请求写进了刚才那个组织」，比 `requireOrg()` 直接抛错难查得多。
- `localStorage` 里不留组织：刷新、收藏、两个标签页开两个组织才不会串。
- v1 的 `/kb/{slug}` 由 `LegacyKbRedirectController` 承接：全局唯一命中 → 301 到 `/kb/{org}/{slug}`；
  多个或零个 → 前端消歧页，数据来自 `GET /api/portal/locate?slug=`。`/admin/**` 整前跳 `/console`，更早的 `/w/**` 301 到 `/console/**`。

### 11.2 `TenantContext` 生命周期

`ThreadLocal<Tenant>`，**只有 `/api/console/{org}/**` 上有值**：`TenantInterceptor.preHandle` 先
`requireBySlug` → `requireMember`（成员门过了才 set，顺序反了会把非成员的 404 变成 500），
`afterCompletion` 一律 `clear()`。它缓存的是「本请求已经解析过的那一行组织」，作用是让同一次请求里的
「解析 slug → 裁决」只查一次，不是跨请求的会话状态。

- 定时任务、异步线程、事件监听器里读到的是 `null`——需要组织就自己把事实传进去，别指望这里。
- `OPTIONS` 预检与 `handler` 不是 `HandlerMethod` 的请求（静态资源）直接放行，不进成员门。

### 11.3 成员门不留痕，动作门留

`requireMember`（§2.6）跑在每个 `/api/console/**` 请求上，在这里写审计等于管理员每翻一页多一条记录，
噪声会淹掉真正要看的条目；「管理员的普通读不留痕」是 F9 的口径。所以成员门只产 404，
动作级越权与超管 `bypass=SUPER_ADMIN` 由 `requireTenant` / `requireKb` 负责记录。
`applyVisibleScope` 同理不留痕（逐字符联想会把审计刷满）。

### 11.4 双轴要同屏，字段就得一起下发

§1.2 把「谁能读」（`visibility`）与「谁能写」（`maintain_scope`）定成正交两轴，UI 就是两个下拉。
因此 `KbVO` 同时带 `visibility` 与 `maintainScope`，`CreateRequest` 也接受 `maintainScope`：
建库时不给，用户就得「建完再调一次改档位接口」，第二步失败会留下一个档位与意图相反的库且没人记得补。
`maintainScope` 不是秘密——看得到这个库的人本来就能看到自己的写权限结论。

- 档位值域只有一个主人：`KnowledgeBase.normalizeMaintainScope(scope, whenMissing)`，建库传默认值
  `owner_only`，改档位的接口传 `null`（省略等于偷偷换成 `owner_only`，会一次清空名单，所以那个接口
  必须 `@NotBlank`）。两个 service 都 delegate，不再各写一份 if。
- `myPermissions` 在**详情、列表、创建**三处都给（列表页要按行决定按钮显隐，只给详情就得逐行再请求一次）。
  **空数组的含义是「本次没算」，不是「什么都不能做」**——门户那几条链路仍走不带权限的 4 参 `KbVO.from`。
  前端据此判断，真判定永远在后端；代价（每行约 8 次主键级判定查询）写在 `KbDtos.KbVO` 注释里。

### 11.5 只读就不去要锁

非维护者（读得到、写不了）打开文档时**不发 `acquireLock`**：那条 403 只会把「你进不来」变成一个请求失败，
再把用户引到「重新获取编辑锁」这个对他无意义的按钮上。只读态由 `myPermissions` 里的 `DOC_WRITE` 直接判定，
锁条文案给全「是谁 / 为什么 / 怎么拿到写权限」（红线 U2），编辑器置 `nocursor` 只读，
而**下载、复制 Markdown、查看渲染仍可用**——它们是读轴，不能跟着写轴一起藏。

### 11.6 前端只读向量，角色字符串只用于文案

- 门禁统一走 `front/src/shared/api/caps.ts` 的 `can(vector, action)`，判定值是后端下发的 `myPermissions`
  / `tenantPermissions` / 分享行的 `canGovern`。页面上允许出现角色字符串的地方**只有文案**
  （成员列表的「拥有者 / 管理员 / 成员」徽标）。唯一的非文案例外是
  `TenantSettingsView` 的 `mustTransferFirst = myRole === 'OWNER'`：那是「你必须先转让才能删」这条事实，
  向量里没有任何动作能表达它。
- 空 / 缺失向量按 **allow** 处理（§11.4：空数组的含义是「本次没算」）。导航是另一回事：
  `AdminLayout` 用严格成员判定，算不出来就不给入口——少一个按钮比给一个点了报 403 的按钮好。
  同理 `governable(row) = row.canGovern !== false`。
- **一条轴是整轴下发的**：`AccessService.permissionsOf` 命中 `DOC_WRITE` 就会把 MAINTAIN 轴全套给出
  （`KB_EDIT_META`、`DOC_WRITE/RENAME/MOVE/DELETE`、`DOC_UPLOAD_ASSET`、`DOC_IMPORT`、`SHARE_CREATE`），
  `permissionsOfTenant` 亦然。所以同轴动作在 UI 上重复设门是噪声（`canWriteKb` 旁边再加一个
  `DOC_IMPORT` 判断不会多拦下任何东西），跨轴的逐个门才有意义。
- 租户 OWNER 一定同时是 ADMIN（`isOrgAdmin()` 含 `isOwner()`），因此审计页读得到成员名单是必然的，
  不需要为「能看审计但看不到人」写兜底分支——那个请求失败只少一个筛选项。

### 11.7 搜索结果的链接由后端拼

`SearchHit.url` 是后端算好的门户地址（`kbUrl(kb, tenantSlugs) + "?path=" + encode(docPath)`），
前端不做拼接。原因和 §11.5 的 `orgSlug` 同源：跨组织可搜，命中的库属于**别人的**组织，slug 只在组织内唯一，
前端手里既没有可靠的 org 段、也不该再为每条命中反查一次。改名、移动、组织段变化只需要改一处。

- 面板里 L1（名称 / 标签联想）与 L2（正文扫描）是**两个桶**，各自 200ms / 500ms 防抖：正文扫描有界但仍是
  全库遍历，不能跟着逐字符的联想一起发。请求带 `seq` 世代号，回来时不是当前世代就丢弃，
  否则慢的那次会覆盖快的、用户看到的是上一轮输入的结果。
- L2 无结果与「还没扫完」要分开说（`正在扫描可见知识库的正文…`），否则用户会把等待读成「没有」。

### 11.8 阅读端给维护者一个「编辑」入口

`ReadView` 带 `orgSlug` 与 `canManage`（后者 = `accessService.can(kb, user, DOC_WRITE)`，`user` 为 null 时
直接 false，游客分支不用另写判断）。链接是 `/console/{org}/kbs/{slug}?path=...`：**组织段取自负载而不是地址栏**——
门户的 URL 形态会变（分享链、老链接 301、消歧页），地址栏里未必留着可解析的组织段。
空库时同一个判据决定按钮文案是「去工作区新建」还是「前往管理后台」。

### 11.9 审计筛选：条件进地址，过滤进 SQL

- `page/size/action/actor/from/to` 全部写在地址栏里（`reload()` 同步回去）：一条带条件的链接发给同事，
  对方看到的必须是同一批条目。任一筛选变化回到第 1 页，否则「第 7 页 + 新条件」是一个空列表，
  读起来像筛不出东西。
- 筛选**下推到 SQL**，`total` 才是真总数；绝不在内存里过滤当前页。上界取 `to.plusDays(1)` 且用 `lt`，
  这样 `from=to=同一天` 覆盖整天，而不是只留 00:00 那一瞬。
- 地址里的值是外部输入：`from`/`to` 必须都是合法 `yyyy-MM-dd`、`action` 必须在已知列表里，否则**当作不筛**，
  而不是拿脏值去查。理由是错的方向不同——脏值查出的空列表会被读成「没人干过这件事」。
  后端配套：`TimeUtil.parseDate` 对无法解析的串抛 `IllegalArgumentException`（不是 `DateTimeParseException`），
  由 `GlobalExceptionHandler` 出 400；否则手改地址栏日期会打成 500。
- 动作下拉的选项跟着**后端真正写过审计**的动作走，不是 `KbAction` 全枚举：大部分读写动作不留痕（§11.3），
  列出来永远筛不出结果。强制解锁是 `KB_MEMBER_MANAGE` + `detail.op=forceUnlock`，没有独立的
  `DOC_LOCK_FORCE_UNLOCK` 这个 action；超管越权行的 action 是被绕过的那个动作本身（`detail.bypass`），
  也不在列表里。
- 组件约束记两条，都是实测出来的：Element Plus 的 `el-select` 把 `''` 当成「没有选中」而显示占位符，
  「全部」这种默认项要用哨兵值（这里是 `'all'`）；单向绑定（`:model-value`）的 change 事件**不会**写回状态，
  默认值来自地址栏时必须显式赋回，否则换选项等于没换。

### 11.10 导航栏只放导航与身份，动作留在页面里

两条栏（门户 / 阅读端的 `user/components/TopBar.vue`、组织管理端的 `admin/layouts/AdminLayout.vue`）
统一按这一条裁剪：

- **栏内只留三类东西**：回首页的品牌、全站搜索、身份（组织切换器 + 用户菜单）。
  「新建知识库」「进管理后台」这类动作要么属于某个具体页面（门户首页筛选栏、知识库管理页表头），
  要么收进身份菜单。顶栏是每页都在的全局件，往里加按钮等于给每个页面都加一份噪音——
  管理端顶栏那个搜索框和「新建」按钮就是这么被删掉的：页面里已经各有一个更好的。
- **导航项按「组织 / 个人 / 站点」分组，两组在任何管理页都在**。之前是「进了组织只剩组织项，
  出了组织只剩个人项」，切换组织时整条侧栏换掉，人不知道自己在哪。分组之后位置变化只体现在高亮上。
  「审计日志」这一项仍按组织的动作向量决定给不给（§4.2），导航是严格判定（§11.6）。
- **图标用真 SVG，不用 `◱ ▤ ⏱` 这类 Unicode 字符**：不同系统字库里会缺字或错位。
  管理端在 `admin/components/MdIcon.vue`，门户 / 阅读端在 `user/components/Icon.vue`，两份不合并是因为
  阅读端首屏 chunk 不能带 EP（§11.1 的 F11），图标集各留各的最小集。
- **`router-link` 而不是 `href="javascript:void(0)"`**：中键 / 新标签页打开和键盘焦点都靠前者。
- **顶栏的下拉全部自己实现**（`position: fixed` + JS 定位 + `pointerdown` 捕获阶段外部点击 + Esc 收起）。
  用 `pointerdown` 不用 `click`：`click` 会先让被点元素完成一次跳转。收起必须走单一函数，
  把「改状态」和「摘监听」绑在一起，否则再打开一次会挂上第二份监听。
- 阅读端的用户菜单要 `position: fixed`：阅读页有若干 `position: sticky` 层（顶栏、侧栏、大纲、
  粘性条），`absolute` 的下拉会被这些层按 DOM 顺序盖住。

### 11.11 可见性三档必须在每一处都成三档

`public / org / private` 是读轴（§2.2）。任何只认两档的显示位都会把 `org` 归进「私有」，
而用户读出来的意思是「这两档是一回事」——`org` 恰恰是团队库最常用的那一档。已知的落点，
新增展示位时逐条对齐：门户页签（`全部 / 公开 / 本组织 / 私有`）、卡片徽标配色、阅读页侧栏文案、
管理端小章配色（知识库管理页两种读法、系统概览、工作区顶栏）、**统计卡与 `StatsVO`**。

小章配色由 `shared/visibility.ts` 的 `visibilityChipClass()` 一处给出，页面不再各自写
`{ 'md-ad-chip--private': visibility === 'private' }`——那种两分支写法正是 `org` 被吞进去的地方。

`StatsVO` 早先是 `kbPrivate = kbTotal - kbPublic`，`org` 库被静默算进私有；现在是
`kbPublic / kbOrg / kbPrivate` 三档各自数，并有断言锁住「三档之和 == 总数」
（`PermissionBaselineTest.visibilityBucketsAreDisjoint`）。

配色走 `shared/styles/variables.css` 的 `--md-vis-public / --md-vis-org`（含 `-bg`），
**深色档必须单独提亮**：`#15803d`、`#7c3aed` 压在 `#0f1117` 上对比度不足 3:1，几乎读不出。

### 11.12 开发库必须开 WAL 并给 busy_timeout

`application-dev.yml` 的 SQLite URL 带 `?journal_mode=WAL&busy_timeout=5000`，这不是调优项：
Hikari 池有 8 条连接，而 SQLite 默认 `busy_timeout=0`，两个写请求撞上（最省事的一条路径是连着切两次
视图，每次都会 `PUT /api/settings`）时第二条直接 `SQLITE_BUSY`，接口打成 500。
WAL 让读不挡写，5s 等待窗口让写请求排队而不是报错。生产 MySQL 无此问题。

### 11.13 全站只有一个滚动区，页面本身不滚

产品要求「任何页面都不出现页面级滚动条，页面高度等于视口高度」。落地方式是一个应用级滚动区，
不是每页各自设高度：

- `body.md-page { height: 100%; overflow: hidden }`，`#app` 为 `flex-direction: column`、
  高度 `100dvh`（**必须带 `100vh` 回退行**：移动浏览器地址栏收起时 `100vh` 是收起前的高度，
  底部那一截既看不见也滚不到，正好是这条要求下最糟的失败方式）。
- `App.vue` 把 `router-view` 包进 `#md-view.md-view`（`flex: 1; min-height: 0; overflow-y: auto;
  overscroll-behavior: contain`）。**新页面不要再自己造滚动容器**，管理端是例外：
  它本身就是「一屏 + 左右分栏内部滚」，`.md-admin` / `.md-ws` / `.md-content` 取 `height: 100%`
  （不是 `100vh`，它的父级已经是扣除顶栏后的那一屏）。
- 顶栏从 `position: sticky` 改成 flex 成员（`flex-shrink: 0`）。于是阅读端内部所有
  `sticky` 元素的偏移基准从 `var(--md-topbar-height)` 变成 `0`，侧栏/大纲的高度要照抄
  `calc(100dvh - var(--md-topbar-height))`——写成 `100%` 会等于整篇正文的高度。
  分享页没有顶栏，`[data-mode='share']` 下这两个高度回到 `100dvh`。

三个连带改动的落点，新增滚动逻辑时逐条对齐：

1. **事件源**：`window` 上再也收不到 `scroll`，读 `window.scrollY` 永远是 0。
   谁要滚动谁取 `shared/scrollRegion.ts` 的 `viewEl()`（`useScrollSpy` 就是这么改的）。
2. **位置恢复**：Vue Router 的 `savedPosition` 同样基于 `window`，一律是 0。
   前进/后退的位置由 `rememberScroll` / `restoreScroll` 自己记。
   **记录必须在 `beforeEach` 里做，不能在 `scrollBehavior` 里做**：`scrollBehavior` 是在新页面
   渲染完之后才调的，那一刻旧内容已经被换掉、`#md-view.scrollTop` 已被浏览器夹回 0，
   记下来只会把真实位置覆盖成 0（这条是踩过一次才写下来的：实测恢复后只有一次 `scrollTop=0` 的写入）。
   `restoreScroll` 逐帧重试到「可滚高度真的容得下目标值」，因为阅读页正文是挂载后异步拉回来的。
   `scrollBehavior` 里 `{ top: n }` 那种写法**不适用**——它滚的是 window，不是 `#md-view`。
3. **打印**：`@media print` 必须把整套「视口高度 + 内部滚动」退回文档流
   （`html, body { height: auto; overflow: visible }`、`#app { display: block }`、
   `.md-view { overflow: visible }`），否则一篇长文只印得出滚动区当前那一屏。
